# Security model

Report a suspected issue through the repository's **Security → Report a vulnerability** link when available. Do not put tokens, private site content, or sensitive diagnostic details in a public issue. If private reporting is unavailable, contact an OpenHoo repository maintainer privately first.

## Boundaries

- The MCP endpoint accepts revocable personal keys or an OAuth access token for its configured issuer and audience. The browser flow verifies an ID token separately. Signed identity claims supply subject, workspace and the maximum role. Personal keys resolve to their enrolled owner; workspace policy and key scope can only reduce that role; headers from a reverse proxy do not grant a role. Development identity works only on a loopback listener with loopback hosts and no forwarding headers.
- A viewer can read workspace content including previews. An editor can create sites and change drafts. Publishers and admins can publish, roll back, restrict audience and request public visibility. Only admins in the workspace explicitly configured by the operator can fetch instance metrics; the production scrape endpoint is disabled by default. The workspace is the collaboration boundary: drafts are not private from other authenticated workspace readers. Use separate workspaces when groups must not read the same private content. Groups within a managed workspace control editing and publishing.
- Draft and live content run on different origins from the control service. Work accounts use authorization code flow with S256 PKCE, state, nonce and a fixed OIDC callback; the site receives a host-bound, short-lived session through a one-time handoff. Sessions are signed/encrypted and host scoped. Site-wide sign-out at the IdP does not instantly invalidate all previously issued browser sessions: they last up to 15 minutes, bounded by ID-token expiry. Keep API access-token lifetimes short. Emergency key rotation invalidates all browser sessions and outstanding signed URLs on every replica.
- The management UI runs on the control host. Enrollment requires verified work identity; no local signup form assigns roles. A workspace admin can restrict or suspend members and revoke keys. Each personal key has 256 random secret bits, is displayed once, is stored as a digest, and expires. A delegated upload or approval rechecks its source key. Removing the identity at the provider alone does not revoke personal keys; see [offboarding](docs/operations.md#accounts-and-offboarding). Account and content changes use CSRF protection in browser forms.
- Uploaded HTML, CSS and media pass validation before storage. A single local classic script can opt a page into the [isolated runtime](runtime/README.md). An authorized read selects the script and page from the same immutable revision. The script source is inert data, including when fetched directly. Only the trusted nonce-bearing bridge runs as native page JavaScript; a dedicated worker interprets the guest in QuickJS. Bounded primitive messages update selected text and controls. Guest code has no browser network, storage, HTML insertion or navigation API. Users can still choose to follow ordinary HTTPS links. Plain pages keep script execution disabled. Operators can disable the runtime instance-wide with `SHOOWCASE_INTERACTIVE=false`. The third-party interpreter and this integration have not had an independent professional audit.
- No build hooks or tenant code execute on the server. ZIP files are validated in memory with limits on entry count, paths, compression, expanded size and file types. Entries are never extracted to a filesystem. The entire draft update succeeds or fails together. All tenant bytes pass through authorization; there is no public bucket that bypasses it.
- Public sharing is off by default. When the deployment enables it, publishers can approve the exact public change over MCP or in the browser. An MCP approval must come from the same account and workspace; a request made with a personal key must use that same key. The signed token expires after five minutes and binds the operation, target and publication state. A later audience or release change invalidates an outstanding approval even when the live content returns to the same revision. Rollback preserves the current audience. Changing a public site to private blocks new managed requests; previously downloaded copies cannot be recalled.
- Upload tickets are short-lived write capabilities limited to an exact path, digest, size, workspace, revision and request ID. Do not put tickets, query strings, Authorization headers, user content or cookies in logs. Redact the entire query string at the ingress. Use a browser only when the author needs to select a local file.
- The service uses parameterized SQL, shared one-time replay records, idempotent mutation results, workspace-scoped writes and optimistic revision checks. Changes are recorded transactionally in the [workspace audit log](docs/audit.md). The database administrator can modify it. Export events to an independently protected audit sink if your retention policy requires tamper resistance.
- This service expects trusted operators, a private database and a correctly configured TLS ingress. Set limits at the edge for connection count, request throughput and bandwidth across all replicas. Application limits protect the process and individual workspaces; they are not a substitute for an edge limit.

The project provides automated security tests, dependency scanning and recovery verification. These are not a penetration-test certificate, regulatory attestation or availability guarantee.

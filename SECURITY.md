# Security model

Report a suspected issue through the repository's **Security → Report a vulnerability** link when available. Do not put tokens, private site content, or sensitive diagnostic details in a public issue. If private reporting is unavailable, contact an OpenHoo repository maintainer privately first.

## Boundaries

- The MCP endpoint accepts an access token for its configured issuer and audience. The browser flow verifies an ID token separately. Only signed claims supply subject, workspace and role; headers from a reverse proxy do not grant a role. Development identity works only on a loopback listener with loopback hosts and no forwarding headers.
- A viewer can read workspace content including previews. An editor can create sites and change drafts. Publishers and admins can publish, roll back, restrict audience and request public visibility. Only admins can fetch instance metrics. The workspace is the collaboration boundary: drafts are not private from other authenticated workspace readers. Deploy one workspace per access group.
- Draft and live content run on different origins from the control service. Work accounts use a fixed OIDC callback; the site receives a host-bound, short-lived session through a one-time handoff. Sessions are signed/encrypted and host scoped. Site-wide sign-out at the IdP does not instantly invalidate all previously issued browser sessions: they last up to 15 minutes, bounded by ID-token expiry. Keep API access-token lifetimes short. Emergency key rotation invalidates all browser sessions and outstanding signed URLs on every replica.
- Site contents are passive. The server validates HTML, CSS and raster types and sets Content Security Policy and no-sniff headers. Uploaded scripts, remote resource imports, forms, build hooks and execution of uploaded code are outside the product. All delivery goes through authorization; no public bucket or object URL bypasses it. Browser navigations to HTTPS hyperlinks can leave the site.
- Public sharing is off by default. Enabling the deployment setting permits publishers to request a transition; the change takes effect only after browser approval. The approval is bound to the actor, workspace, operation, target revision and the site’s publication state. A later audience or release change invalidates an outstanding approval even when the live content returns to the same revision. Rollback preserves the current audience. Changing a public site to private blocks new managed requests; previously downloaded copies cannot be recalled.
- Upload tickets are short-lived write capabilities limited to an exact path, digest, size, workspace, revision and request ID. Do not put tickets, query strings, Authorization headers, user content or cookies in logs. Redact the entire query string at the ingress. Use a browser only when the author needs to select a local file.
- The service uses parameterized SQL, shared one-time replay records, idempotent mutation results, workspace-scoped writes and optimistic revision checks. Audit data is transactional. The database administrator can modify it. Export events to an independently protected audit sink if your retention policy requires tamper resistance.
- This service expects trusted operators, a private database and a correctly configured TLS ingress. Set limits at the edge for connection count, request throughput and bandwidth across all replicas. Application limits protect the process and individual workspaces; they are not a substitute for an edge limit.

The project provides automated security tests, dependency scanning and recovery verification. These are not a penetration-test certificate, regulatory attestation or availability guarantee.

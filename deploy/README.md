# Operating and releasing Shoowcase

## Run the production image

Deploy the OCI digest from the release's `image.txt` after checking its `SHA256SUMS` and GitHub provenance (`gh attestation verify SHA256SUMS --repo openhoo/shoowcase`). The image contains the Go service, a CA trust bundle, and the Apache LICENSE and NOTICE. It runs as UID/GID 65532 and needs no writable root filesystem, mounted volume, Docker socket, Linux capabilities or privileged mode. Site data and one-time sign-in records live in PostgreSQL. Use the release controls below to choose which source and publisher you trust; a checksum alone authenticates neither.

1. Provision a dedicated PostgreSQL database and user with permission to own/migrate Shoowcase's tables in its schema. Set a TLS-verified connection string (for instance, `sslmode=verify-full`). Never use the disposable CI database or its credentials.
2. Provide a control HTTPS origin and a wildcard HTTPS route on a **separate registrable domain** for content; for example, `studio.example.com` and `*.sites.example.net`. Route both to the service and preserve the original Host header. Configure the ingress to reject unknown hosts and never cache control responses, authenticated pages, or preview URLs. Do not log request query strings, authorization headers, cookies, form bodies or uploads. Pass rate and body-size policies at ingress.
3. Register one confidential browser OIDC client. Its only callback is `https://studio.example.com/auth/callback`. Configure the issuer to return a nonempty subject, one active workspace string and roles (`viewer`, `editor`, `publisher` or `admin`) in ID tokens and access tokens. For MCP, register an API audience distinct from the browser client. The resource URL is `https://studio.example.com/mcp`; configure the IdP to issue a signed JWT access token with header type `at+jwt`, this audience and the required claims. Browser cookies do not authorize MCP.
4. Supply the environment variables required in [compose.yaml](compose.yaml) using your secret manager or process supervisor. Generate the shared session key with `shoowcase keygen` and store it directly in secret custody; rotating it invalidates active sessions and tickets. Pass the release's exact image reference as `SHOOWCASE_IMAGE`. Keep `SHOOWCASE_PUBLIC=false` until workspace-private publication and recovery have passed acceptance.
5. Start with `docker compose -f deploy/compose.yaml up -d` behind your existing TLS reverse proxy. Only port 7878 on host loopback is exposed. Verify the control-host `/healthz`; configure ingress to pass an allowed Host for probes.
6. Sign in against the actual issuer, publish/read from one workspace and verify another workspace and anonymous browser cannot read that private release or its assets. Test a public change, rollback, preview access, and metrics with appropriate roles. Restore a real backup into a **separate** database and exercise private site access on the restored instance before relying on it. Record your restore time and retention policy.

The Compose example uses external ingress and PostgreSQL. It starts a single application replica. For multiple replicas, use the same PostgreSQL database, session key and URL configuration; apply aggregate limits at the ingress and prove rolling updates, availability and restoration for your deployment. A hosted container and a passing CI workflow do not establish a production SLO.

## Install the agent skills

Each release from v0.1.1 includes `shoowcase-vX.Y.Z-skills.zip`, where `vX.Y.Z` is the release tag. It contains `shoowcase-publish/SKILL.md`, `shoowcase-operate/SKILL.md`, `LICENSE`, and `NOTICE`. The skills document agent workflows; they grant no account permissions.

1. Download the ZIP and `SHA256SUMS` from the same release. For a trusted release tag, verify the ZIP's GitHub build provenance with `gh attestation verify shoowcase-vX.Y.Z-skills.zip --repo openhoo/shoowcase`. Check its SHA-256 against the matching line in `SHA256SUMS`.
2. Extract it to an empty directory and review the skill you want. Copy the entire `shoowcase-publish` directory into a site author's agent skills folder, or `shoowcase-operate` into a maintainer's agent skills folder. Keep the license and notice with redistributed copies.
3. Connect authors to the instance's MCP URL. Maintainers run the operator skill from a checkout of the matching Shoowcase release.

## Verify or release

- For development, `make build test vet`, `make smoke`, and `make vuln`. Set `SHOOWCASE_TEST_POSTGRES_DSN` only to an **isolated, disposable** database when running backend integration tests.
- The `CI` workflow's job is **verify**. It runs vet, race tests with a disposable PostgreSQL 17 service, a pinned govulncheck against the live Go vulnerability database, a smoke test against the binary, a backup/restore test against a separate database, and a read-only nonroot OCI image check. The runner needs access to GitHub, the Go module and checksum services, the Go vulnerability database, and the container registry.
- Before publishing, protect main, require the `verify` check and code review, restrict updates/deletion of release tags `v*`, and restrict the `release` environment to approved publishers. Where the repository plan permits, enable GitHub immutable releases and disallow mutable release tags. Leave default workflow permissions read-only. The release image job alone needs package write; publishing the binary release needs contents write. The release remains in the repository/package visibility you configure.
- Push a stable annotated tag `vX.Y.Z` on main when explicitly ready to publish. The tag workflow repeats verification, builds and pushes the Linux amd64/arm64 image to GHCR, verifies its published index, then uploads four binary archives (Linux amd64/arm64, macOS arm64, Windows amd64) with LICENSE and NOTICE in each archive, a separate versioned ZIP containing both agent skills, checked per-binary Go module metadata, SPDX 2.3 and CycloneDX 1.5 SBOMs, image reference and checksums. The release jobs attach GitHub SLSA provenance to the OCI index and to every release asset. Verify it with `gh attestation verify ARCHIVE --repo openhoo/shoowcase` or `gh attestation verify oci://ghcr.io/openhoo/shoowcase@sha256:… --repo openhoo/shoowcase`. Finally it downloads the GitHub assets and checks the bytes. A partial failure can leave an image without release assets: inspect the registry digest and failed job before retrying. Do not move an already published tag.
- With Actions unavailable, build artifacts locally on a trusted checkout of the desired commit using the pinned Go 1.27.4 toolchain and Python 3: `scripts/release.sh vX.Y.Z /path/to/empty-output`. This command **only builds files**. To include an independently published OCI digest in those files, set `SHOOWCASE_RELEASE_IMAGE=ghcr.io/openhoo/shoowcase@sha256:…` beforehand. Verify from the output directory with `sha256sum -c SHA256SUMS` (macOS: `shasum -a 256 -c SHA256SUMS`). Run the same vet, race, database, vulnerability and smoke checks as CI before distributing local artifacts.
- Build locally with `make image ENGINE=podman VERSION=vX.Y.Z`. Run `podman run --rm --read-only --cap-drop=all --security-opt=no-new-privileges --network none shoowcase:vX.Y.Z version` to confirm the binary and image tag agree.

Update action pins against the official action git repositories and container pins against the image registry's OCI index. Test supported architectures and the service smoke flow after each update. Keep toolchain versions aligned in the Dockerfile, workflows and local release script.
